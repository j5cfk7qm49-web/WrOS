# Technical, security and licensing risk register

This register began with software, simulation and VM verification. Treat those results as historical unless tied to the current source. Hardware, disk-installation and provider results must name the release, device or account, and exact checks performed.

## Practical implementation lessons

Historical Debian image-builder lessons: the first VM attempts exposed a GRUB embedded-prefix/config loading problem; embedding the final menu removed the dependency on a missing external module. That image assembly reset regular artifact files to zero length before sparse reconstruction so stale bytes cannot survive a rebuild. Keymap generation also required `loadkeys --unicode --bkeymap` for container-safe validation. These are tested corrections, not reasons to skip actual boot verification.

The first real console screenshot exposed lingering login/splash characters where a terminal does not implement an alternate screen. The application now explicitly clears the terminal once during initialization. Keep VM screenshots as actual evidence, not interface mockups.

## When to ask for authorization

Ask before any physical partitioning/formatting, LUKS setup/recovery-secret handling, privileged live-host installation, authentication/credential exchange or intentional hardware power action performed by the development agent. Writing code and testing disposable regular-file VM artifacts is not authorization to install on the user's laptop.
