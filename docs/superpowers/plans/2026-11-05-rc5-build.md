# rc5 build plan (everything but phone linking)

> **For agentic workers:** executed inline (superpowers:executing-plans). Steps are TDD:
> failing test, watch it fail, implement, watch it pass, commit.

**Goal:** Build rc5's sections 2–5 and the site groundwork from the design, leaving
section 1's laptop end (linking) until the phone test on 2026-11-06 settles whether the
no-Wi-Fi "one scan" path replaces or backs up the Wi-Fi path.

**Spec:** `docs/superpowers/specs/2026-11-04-rc5-backups-and-recovery-design.md`

**Tests run in the Debian 13 chroot** (`ct.sh` in the session scratchpad syncs the
checkout to `/home/aegeorge/wros-src` and runs there): Python with
`python3 -m unittest discover -s os/tests -p '<pattern>'`, Rust with
`cargo test --locked --offline -j2`. Baseline: `test_update*.py` 50/50.

## Global constraints

- Anti-goals from the spec hold everywhere: no backup reported without a verified
  restore; a rollback installs only bytes this computer verified and installed before;
  recovery asks for the WrOS account password.
- The update engine's existing protocol stays: journal before trigger, `exclusive()` lock,
  re-verification against the pinned keyring whenever retained bytes are used.
- Anti-replay stays monotonic: `replay.json` never moves back. A rollback is the single,
  explicit exception, and only for the retained previous tree.
- No secrets in logs, journal or responses. Nothing contacts Google or the network unless
  the writer or an existing scheduled check already does.

## Task order (most valuable and least test-dependent first)

### Task 1: the site's static pages land in development
Files: `pages/index.html`, `pages/privacy/index.html`, `pages/l/index.html`,
`pages/link/index.html` (Wi-Fi flow only, no mailbox code), `.github/workflows/release-updates.yml`
("Static pages" step, tags `['v*', '!v*-linktest*']`), `os/tests/test_update_workflow.py`.
- Test: the workflow copies `pages/.` into `out/pages` before the Pages artifact, only when
  deploying; spike tags never trigger; the deploy-gate count is updated.
- Privacy wording: the one-use code passes through the site's address on its way to the
  laptop and is useless without the laptop's half of the PKCE pair.
- `/l2/` and the mailbox half of `/link/` stay out until the phone test decides them.

### Task 2: the engine keeps the installed tree and the one before it
File: `os/scripts/wros-update-engine.py`; test: `os/tests/test_update_rollback.py` (new).
- `Store.installed = dir/'installed'`, `Store.previous = dir/'previous'`.
- After a `completed` record (boot or live apply, not a rollback): `installed/` → `previous/`
  (old `previous/` removed), then `staged/` → `installed/` (rename, not delete).
- `Store.publish` adds `previous_version` (the package labels of `previous/`'s manifest,
  or `None`).
- Tests: apply twice → `previous/` holds the first bundle, `installed/` the second;
  the first apply leaves no `previous/`; a failed apply rotates nothing.

### Task 3: going back, by hand
Files: engine; new launcher `os/scripts/wros-update-rollback`; polkit action
`org.wros.update.rollback` (policy + rules); `packaging/manifest.json`; test file from Task 2.
- `stage_rollback(*, state_dir, trigger_path, dpkg_dir, keyring, signers, now, host_arch)`:
  re-proves `previous/` with `revalidate_staged(..., mode='rollback')` (signature, pin,
  hashes; no age or replay check), requires every package to be a downgrade of the
  installed version, copies it to `staged/` with a new transaction id, `rollback: true`,
  `rollback_of: <installed review id>`, and stages it with the same journal-then-trigger
  protocol. Live-apply is allowed when the downgrade is app-only.
- `revalidate_staged(mode='apply')` on a manifest with `rollback: true`: skips the replay
  check only if its `review_id` equals `previous/`'s; evaluates with downgrades allowed.
- `apt_command(..., allow_downgrades=True)` adds `--allow-downgrades`.
- After a completed rollback: `previous/` → `installed/`, the replaced tree is discarded,
  `replay.json` unchanged, journal `completed` carries `rollback: true`.
- Tests: rollback stages and applies; refused with no `previous/`; refused when a retained
  byte changed; refused when the installed version is not the one `installed/` recorded;
  the rolled-back-from version cannot be staged again (replay); a forged
  `rollback: true` on a different tree is refused.

### Task 4: rc5's own bytes become the first "installed" tree
rc4's engine installs rc5 and deletes `staged/` afterwards, but an online update leaves its
verified download in `/var/cache/wros-update/online/<16 hex>/`. `reconcile` adopts it as
`installed/` when its review id is the one `replay.json` records and its packages are what dpkg
has installed (verified as of its own release date). No maintainer script is needed.
Tests: adopted, then usable as previous; a different cached bundle is ignored; nothing is
adopted over an existing `installed/`.

### Task 5: probation and the automatic go-back
Engine + `wros-update-reconcile.service` + launcher verb `healthy`
(`wros-update-healthy`, polkit `org.wros.update.healthy`).
- A completed update (not a rollback) writes `probation.json` `{tx_id, boots: 0}`.
- `reconcile` (every boot, before greetd) increments `boots`; at `boots > 2` it stages a
  rollback, journals `auto_rollback`, and reboots into the offline apply.
- `healthy` clears probation. Public status shows `probation` and the last automatic
  go-back so the app can say so after login.
- Tests: counter, threshold, clear, no rollback without `previous/` (journals why).

### Task 6: the app side of going back
`crates/writingdeck-sys` (invocations, `UpdateInfo` fields), `src/app/shell*`:
Settings › Updates "Go back to <version>" with a confirm screen; one `healthy` call after
the first frame when status shows probation; a notice after an automatic go-back.
Rust UI tests.

### Task 7: automatic backups and retention
`os/scripts/wros-backup` (`backup` takes `automatic: true` → tag `auto`; new `prune`
operation: computes the keep set itself — all auto snapshots of the last 7 days, the newest
per day for 90 days, the newest per ISO week after — then `restic forget <ids>` +
`prune`; manual and named snapshots never), `src/app/backup.rs` scheduler (10 min pause,
at most hourly, backoff 15 min/1 h/4 h, status line "Backed up 14:02 · verified").
Tests: Python for the keep set and the auto tag; Rust for the scheduler timing.

### Task 8: the system profile
Each backup stores `wros-profile/` beside the book, recorded separately in the manifest
so the book's verified-restore comparison is unchanged; restore offers "Restore settings
too". Contents decided in the task (Grimoire settings, WrOS preferences, keyboard,
timezone, books list), never the recovery key, Wi-Fi passwords or the Google token.

### Task 9: recovery boot
GRUB entry, `wros-recovery.target`, a console menu (`wros-recovery`) behind the account
password, choices per the spec, shown in the menu only after a failed boot.

## Review focus

1. A rollback must never install bytes other than the retained previous tree, even if
   `staged/manifest.json` is edited.
2. Power loss between rotation steps leaves a usable `installed/` or `previous/`, never
   neither silently.
3. Probation must not roll back a healthy system that the writer simply powered off at the
   login screen twice (decide: count only boots that reached the greeter? recorded in the
   ledger when Task 5 is built).
4. Retention must never forget a manual or named snapshot, or the only verified one.
5. Automatic backups must never run while words are unsaved.
